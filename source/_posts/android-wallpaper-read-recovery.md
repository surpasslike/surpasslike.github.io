最近整理桌面壁纸的加载逻辑时，我把一个容易被忽略的问题重新梳理了一遍：**壁纸暂时读不到之后，页面应该怎样恢复？**

正常路径很短：读取当前选择，找到图片，再显示出来。进入异常路径以后，要回答的问题就多了：之前的图片还在不在？这次失败会不会覆盖用户的选择？用户回到首页时是否再试一次？上一轮请求的回调迟到了，会不会改掉新一轮的状态？

这篇记录围绕这些问题展开。具体实现使用了 Compose，恢复策略也适用于其他异步图片页面。

## 为什么文件完好，画面还停在旧图

排查时发现，旧实现一旦收到图片加载失败回调，就会记住失败状态，并把加载组件换成只显示旧图的组件。这个状态只随图片身份或文件引用变化而重置。在同一次组合里，即使数据层复核后确认文件完整，用户回到首页时仍然只会看到旧图。文件和选择都没变，加载组件就没有机会重新创建。

这里需要补的是同一张图的再次读取机会。保留旧图可以减少画面跳变，继续保留用户选择则让下一次读取仍然指向原来的目标。

## 先分清两种“读不到”

排查时，第一步是确认失败发生在哪一层。

| 失败位置 | 这一层负责什么 | 恢复时需要保留什么 |
|:---|:---|:---|
| 配置快照读取 | 获取用户当前选择的壁纸及相关信息 | 最后一次成功读取的快照 |
| 图片加载或解码 | 把选中的资源转换成可以显示的图片 | 当前仍可用的旧图，以及用户原来的选择 |

配置快照拿到了，图片仍然可能加载失败；图片没有显示出来，也不能据此认定配置已经损坏。

如果把这两层的异常都交给一个“恢复默认”的分支，显示问题就可能扩大成配置问题：页面只经历了一次读取失败，用户的选择却被重置了。

因此，我给这里加了一条约束：**读取失败时允许界面回退，但不能顺手把默认壁纸写回用户配置。**

首次进入时没有可用快照，可以先显示默认背景；已有成功快照时，继续保留它。这两种情况都不需要通过写配置来完成兜底。

图片层报告读取失败后，数据层会核验当前引用指向的主媒体文件。确认文件缺失、类型或长度异常，或者已记录的内容摘要不符时，才移除这条引用并修正受影响的选择。原文件保留。核验时遇到无法判定文件状态的 I/O 异常，则把异常交给调用方，保留已有配置。

这里用了 `Files.readAttributes`。`Files.isRegularFile` 在文件不存在、类型不符或无法判定时都可能返回 `false`。需要根据检查结果决定是否修改持久化数据时，读取文件属性可以让调用方区分这些情况。[Android `Files` API](https://developer.android.com/reference/java/nio/file/Files)

## 新图成功以前，先保留旧图

另一个影响体验的地方，是切换壁纸时旧图的处理。

假设页面正在显示壁纸 A，用户选择了壁纸 B。如果刚发起 B 的读取就清空 A，页面会先露出默认背景；随后 B 加载成功，页面又变化一次。B 如果失败，用户看到的就只剩默认背景。

这里更合适的显示顺序是：

```text
显示 A
  → 开始读取 B，继续显示 A
  → B 成功：显示 B
  → B 失败：保留仍可用的 A，等待后续恢复机会
```

如果没有可用旧图，才使用默认背景。这里的“保留旧图”有明确边界：旧资源本身仍需可用，缓存和资源管理也要遵循现有实现，不能把它理解成无限保留所有历史图片。

这也提醒我，用户选择的目标和当前已经显示成功的内容，可以暂时处于不同阶段：目标已经变成 B，当前画面仍然是 A，等到 B 真正可用后再切换。

## 让可见性提供重试机会

读失败以后马上重新请求，很容易形成一条没有出口的循环：

```text
加载 → 失败 → 立即重试 → 再次失败 → 再次重试……
```

对于背景图片，页面离开前台后仍然持续尝试，通常也没有必要。这次实现把重试机会放在页面重新具备展示条件的时候，并且要求上一轮确实失败过。

我把展示条件理解成两个信号的交集：

```text
有效可见 = 首页在当前界面中可见 && 生命周期至少处于 STARTED
```

只看生命周期，可能漏掉同一个 Activity 内部从其他页面返回首页的情况；只看首页的可见标记，又无法完整表达 Activity 已经退到后台的状态。

图片层只在“有效不可见 → 有效可见”的边沿检查失败标记。已经成功的图片不用因此重新加载，处于同一次可见期间的失败也不会立刻触发无限重试。

这里有一个容易写错的细节：**这个条件不等于每次 `onResume` 都会重试。**

完整退到低于 `STARTED` 的状态，再回到前台时，条件会重新成立；但如果只是 `PAUSE → RESUME`，整个过程一直处于 `STARTED` 及以上，首页的可见标记也没变，就不会产生新的可见性边沿。

配置快照通过 `repeatOnLifecycle(STARTED)` 收集。生命周期低于 `STARTED` 时取消收集，再次达到 `STARTED` 时重新收集。快照读取失败并且订阅已结束时，首页重新可见也会触发一次新订阅。图片层和快照层分别维护各自的失败状态。[AndroidX `repeatOnLifecycle` API](https://developer.android.com/reference/androidx/lifecycle/RepeatOnLifecycleKt)

## 同一张图的两次读取，也要能区分

异步回调带来的问题，往往需要放到时间线上才能看清楚。

```text
第 1 轮读取图片 B
  → 第 1 轮失败
  → 页面重新可见，开始第 2 轮读取 B
  → 第 2 轮成功
  → 第 1 轮的迟到回调到达
```

如果回调只比较图片地址，两轮都是 B，旧回调仍然可能改写当前状态。

因此，请求身份需要同时表达资源和读取轮次。重试时，即使资源地址没有变化，也应得到新的请求身份。

下面用伪代码表达这个约束，省略具体图片库和资源管理代码：

```text
当前请求 = (图片身份, 重试轮次)

开始加载时：
    记住本轮请求身份

成功或失败回调到达时：
    如果本轮身份不等于当前请求：
        忽略回调
    否则：
        更新本轮加载结果
```

在 Compose 中，这个请求身份用来重建图片加载节点。重试轮次只进入组件的 `key` 和回调校验。图片缓存仍使用资源身份，同一文件的每次重试可以沿用同一个缓存键。

这里我会重点检查成功和失败两个回调：只拦住迟到的成功回调还不够，迟到的失败回调同样可能把已经恢复的页面重新标成失败。

## 订阅取消要保留原来的含义

快照读取还有另一类需要区分的情况：生命周期降到 `STARTED` 以下，或持有订阅的组合离开时，订阅正常取消。首页在同一个 Activity 内隐藏，本身并不意味着快照订阅已经取消。

如果使用协程收集数据，捕获读取异常时要保留取消的语义。当前实现会把取消异常继续抛出，让上层的生命周期管理完成清理；普通读取失败才进入保留旧快照、等待后续重新订阅的分支。

否则，正常结束订阅可能被错误记录成读取故障，甚至在已经结束的订阅里继续做恢复工作。观察日志时，也就难以区分“读失败了”和“当前订阅不再需要继续”。

## 我会怎样检查这类恢复逻辑

只检查一次正常切换，覆盖不到恢复过程中最容易出错的顺序。我更关注下面这些场景：

| 场景 | 需要观察的结果 |
|:---|:---|
| 首次读取快照失败 | 页面有默认背景，用户选择未被重写 |
| 已有成功快照后读取失败 | 最后一次成功快照仍然保留 |
| 切换图片时新图失败 | 有可用旧图时继续显示旧图 |
| 失败后首页重新可见 | 获得一次新的图片读取机会 |
| 失败后完整退后台再返回 | 可见性恢复时获得重试机会 |
| 仅 `PAUSE → RESUME`，有效可见性未变 | 不误认为产生了新的可见性边沿 |
| 同一图片重试成功后收到旧回调 | 旧回调不能修改当前状态 |
| 生命周期低于 `STARTED`，或持有订阅的组合离开 | 取消正常传播，不当作普通读取失败 |

此前在一台 Android 设备上保留应用数据做回归，壁纸及相关导航共 27 项仪器测试通过。其中一项让绿色测试图的第一次读取主动抛出异常，文件内容保持完好。测试通过采样画面中心像素确认，失败后和重试等待期间都显示上一张红图，第二次读取成功才切换到绿图。另有测试让 Activity 从 `CREATED` 回到 `RESUMED`，确认资源不变时仍可重试。应用日志也记录到了失败、重新可见后重试和恢复成功的顺序。

数据层回归分别构造了摘要匹配、等长字节损坏和文件属性读取抛出异常。摘要匹配时选择保留，等长损坏只移除失效引用并修正选择，属性读取异常则向上传播。整组回归前后比对了设备原有的壁纸与显示配置哈希和媒体目录清单，结果一致。

本次整理核对了修复前后的实现和归档结果。上述实测来自此前的受控故障注入。表里的迟到回调和仅 `PAUSE → RESUME` 是基于代码路径列出的检查项，仍待单独验证。

这套方案针对的是读取和显示阶段的异常恢复。资源被真正删除、权限持续不可用、进程重建后的状态恢复，以及长时间待机等情况，还需要结合各自的资源管理和生命周期路径单独验证。
